# NUBEMO DEV — Architectural cleanup audit (4C.2b)

## Scope

This branch is intentionally non-production. `main` remains the functional baseline.

Cleanup scope:
- no Supabase migrations;
- no RLS/schema/data changes;
- no new features;
- no redesign;
- no intentional behavior changes.

The goal is to identify ownership boundaries and remove the conditions that encourage patch-on-patch changes.

## Current professional-area loading chain

`pro.html`
→ shared CSS (`style.css`)
→ temporary landscape CSS (`professional-patient-landscape.css`)
→ shared libraries / Supabase client
→ `professional-drawer-trigger-fix.js`
→ `professional-guard.js`
→ dynamically loads `pro.js`
→ dynamically loads `professional-patient-management.js`

## Current responsibilities

### `professional-guard.js` — stable boundary
Owns:
- authentication/session verification;
- professional profile loading;
- professional logo loading;
- loading professional/patient relationships from Supabase;
- exposing `window.nubemoProfessionalContext`;
- loading the professional application only after authorization.

Assessment: coherent responsibility. Keep as infrastructure/auth bootstrap.

### `pro.js` — legacy/core monolith
Approximate size: 3.7 MB.

Owns, among other things:
- application state and render flow;
- navigation;
- drawer markup and bindings;
- patient list/detail rendering;
- clinical edit flow;
- agenda and other professional functions;
- substantial responsive behavior assumptions.

Assessment: functional core, but too many responsibilities. Do not rewrite wholesale. Refactor progressively only when an area is touched.

### `professional-patient-management.js` — valid feature, structurally transitional
Owns 4C.2b functionality:
- demographic editing;
- terminate pathway;
- reactivate pathway;
- terminated-patient section.

Current integration technique:
- observes renders with `MutationObserver`;
- discovers/injects UI into DOM generated by `pro.js`;
- sometimes triggers existing UI controls to re-enter the legacy render flow.

Assessment: feature is valid, but the integration pattern must not become the default for future development. Target state is a real patient-management module with explicit render/actions boundaries.

### `professional-drawer-trigger-fix.js` — patch to absorb
Owns only a correction to click behavior on `#openProDrawer` depending on layout.

Assessment: not a final architectural component. The root problem belongs to professional shell/header markup and drawer binding. Target: absorb into shell/navigation ownership and delete this file.

### `professional-patient-landscape.css` — temporary responsive override
Owns targeted patient-header landscape rules.

Assessment: acceptable as temporary containment, not as long-term responsive architecture. Target: consolidate into one controlled professional responsive layer after migration stabilizes.

### `style.css` — shared core with responsive debt
Contains many historical professional responsive overrides and successive iPhone/landscape adjustments.

Assessment: do not append more broad override blocks. When UI stabilization starts, map selectors/breakpoints first and consolidate by component.

## Architecture rules from this point

1. Every new change must have one explicit owner: auth/bootstrap, shell/navigation, patient management, clinical, agenda, PDF, or shared UI.
2. Do not introduce a new `*-fix.js` or end-of-file CSS override as a permanent solution.
3. A temporary compatibility adapter is allowed only when documented here with a planned absorption target.
4. Do not modify `pro.js` blindly. Before changes, locate the owning render function, event binding, state variable and responsive selectors.
5. During Supabase migration, prioritize functional correctness. Non-blocking visual defects go to UI backlog.
6. Blocking/ambiguous functional bugs are fixed immediately.
7. UI consolidation happens after the relevant functional area is migrated and stable.

## Proposed progressive target structure

This is a target map, not an immediate rewrite:

- `professional-guard.js` — auth/bootstrap and remote context only
- `professional-shell.js` — shell, header, drawer, navigation
- `professional-patients.js` — patient list, detail, demographics, pathway lifecycle
- `professional-clinical.js` — clinical sheet and clinical-specific actions
- `professional-agenda.js` — agenda/appointments
- `professional-services.js` — Supabase queries/actions shared by professional modules
- `professional.css` — professional component/layout rules with explicit responsive sections

Legacy functions remain in `pro.js` until migrated area by area.

## Cleanup order recommended

### Phase A — now, before continuing migration
- freeze `main` as working baseline;
- keep all cleanup work on this branch;
- document ownership boundaries;
- stop new patch-file proliferation;
- identify which temporary files must eventually be absorbed.

### Phase B — during Supabase migration
For each migrated area:
1. verify current owner and legacy flow;
2. move data access/state responsibility to the correct module/service;
3. preserve existing UI unless a bug blocks use;
4. regression-test the migrated flow;
5. only then remove obsolete compatibility code.

### Phase C — after functional migration stabilizes
- absorb drawer fix into shell/navigation;
- absorb 4C.2b patient DOM patching into explicit patient rendering/actions;
- consolidate professional responsive CSS;
- perform dedicated UI/UX pass for desktop, iPad portrait/landscape, iPhone portrait/landscape.

## Current risk assessment

### Low risk
- Supabase 4C.2b relationship/status model;
- `professional-guard.js` bootstrap role;
- existing PDF isolation.

### Medium risk
- `professional-patient-management.js` DOM integration;
- global context exposed on `window` as a transitional interface.

### High maintenance risk (not immediate data risk)
- `pro.js` monolith;
- accumulated professional responsive cascade in `style.css`;
- permanent use of small fix scripts/override styles if allowed to continue.

## Decision

Do not pause the Supabase migration for a full rewrite.

Proceed with: **minimal architectural cleanup now → continue Supabase migration with functional correctness as priority → structural/UI consolidation after migrated areas stabilize**.
